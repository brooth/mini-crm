# Мини-CRM «Объекты и задачи»

Учёт строительных объектов и задач по ним с двумя ролями: **постановщик** (manager) и **исполнитель** (executor).
Отдельного бэкенда нет: фронтенд обращается к Supabase напрямую через `supabase-js` с публичным ключом. **Все права проверяет Postgres**: RLS, column-level grants, триггеры и RPC.

## Развернуть свою базу

1. Создать проект на supabase.com (free tier).
2. **Authentication → Sign In / Providers → выключить «Allow new users to sign up».** Самостоятельной регистрации нет.
3. SQL Editor: выполнить [supabase/migrations/20261104000000_init.sql](supabase/migrations/20261104000000_init.sql). Вариант через CLI: `npx supabase link --project-ref <ref> && npx supabase db push`.
4. Authentication → Users → **Add user** (отметить *Auto Confirm User*): `manager@example.com`, `ivanov@example.com`, `petrov@example.com`.
5. SQL Editor: выполнить [supabase/seed.sql](supabase/seed.sql). Он назначит роли и имена и создаст 3 объекта и 6 задач во всех статусах с историей.
6. Project Settings → API: скопировать **Project URL** и **anon / publishable key** в `.env`.
   Ключ `service_role` / secret key не нужен и в проект не попадает.
7. (опционально) `npx supabase gen types typescript --project-id <ref> > src/app/database.types.ts`.
   Сейчас этот файл написан вручную по миграции в том же формате.

Деплой: Vercel → Import repo → Framework Vite → env `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`. SPA-роутинг настроен в [vercel.json](vercel.json). После деплоя: Supabase → Authentication → URL Configuration → Site URL = адрес Vercel.

## Где лежит безопасность

Всё находится в одной миграции [supabase/migrations/20261104000000_init.sql](supabase/migrations/20261104000000_init.sql). Фронтенд только прячет кнопки, которые пользователю недоступны.

| Механизм | Что даёт |
|---|---|
| **RLS** на всех таблицах | Исполнитель получает только свои задачи, объекты, где у него есть задачи, и историю своих задач. Писать в `objects` и `tasks` может только постановщик. |
| **Column-level grants** | В `tasks` клиент может писать только `title, description, object_id, assignee_id`. Если передать `status`, `author_id` или `created_at`, база вернёт `permission denied`. `task_status_history` открыта только на чтение, `profiles` тоже: роль через API не поменять. |
| **Триггеры** | Автор, статус `new` и даты проставляются сервером. Статус нельзя изменить обычным `update`. Исполнителем может быть только пользователь с ролью «исполнитель». При создании задачи в историю пишется первая запись. |
| **RPC `change_task_status`** | Единственный способ сменить статус. Функция проверяет таблицу переходов и роль, требует комментарий для `rework` и сама пишет историю. |
| **Auth** | Регистрация выключена. Новый пользователь всегда получает роль `executor`, повысить её можно только вручную в базе. |

### Проверить

- **На чистом Postgres** (без Supabase), 33 атаки и happy path:
  ```bash
  docker run -d --name crm-pg -e POSTGRES_PASSWORD=pg -v "$PWD/supabase":/sql:ro postgres:16
  P() { docker exec -i crm-pg psql -U postgres -v ON_ERROR_STOP=1 -q "$@"; }
  P -f /sql/tests/00_supabase_shim.sql && P -f /sql/migrations/20261104000000_init.sql
  P -c "insert into auth.users(email) values ('manager@example.com'),('ivanov@example.com'),('petrov@example.com')"
  P -f /sql/seed.sql && P -f /sql/tests/10_security_attacks.sql 2>&1 | grep -E 'PASS|FAIL'
  ```
- **Против живого Supabase** с тем же публичным ключом, что у фронтенда. Скрипт входит как исполнитель и пытается обойти интерфейс: читает чужие задачи, пишет напрямую, подделывает историю, повышает себе роль, вызывает RPC в обход правил, регистрируется сам:
  ```bash
  # в .env дополнительно: MANAGER_PASSWORD, EXECUTOR_PASSWORD; нужен Node 22+ (см. .nvmrc)
  npm run security-check
  ```
  Каждая проверка печатает PASS или FAIL, в конце скрипт сверяет под постановщиком, что данные не изменились.

## Структура

```
src/
├── app/            # каркас из админки: компоненты (формы, карточки, таблицы, тосты), layout, sidebar, topbar; типы БД (database.types.ts)
├── auth/           # сессия Supabase, профиль, AuthGuard, страница входа
├── object/         # объекты: entity, store, hooks, диалог, страницы списка и карточки
├── task/           # задачи: статусы, availableActions, store, hooks, диалоги, история, страницы
└── utils/          # supabase-клиент, ApiCallState, useFormData, useApiErrors и т.п.
supabase/           # миграция, seed, SQL-тесты атак
scripts/            # security-check.ts
```

Паттерн данных взят из референсной админки. В zustand-store лежат только состояния запросов (`ApiCallState`) и сеттеры. Запросы к Supabase живут в `*.hooks.ts`. После мутации связанные состояния сбрасываются (invalidate), и открытые страницы сами перезагружают данные. При смене пользователя все store очищаются.

[src/task/task.actions.ts](src/task/task.actions.ts) повторяет таблицу переходов из базы, но только решает, какие кнопки показать. Разрешение на переход даёт RPC.

## Решения и допущения

1. Роли хранятся в `profiles`. Новый пользователь всегда исполнитель, повысить роль можно только вручную в базе. Через API роль не меняется.
2. Постановщик может редактировать и переназначать задачу в любом статусе, а также удалять её. Вместе с задачей удаляется её история. Удаление объекта удаляет его задачи.
3. Исполнителем можно назначить только пользователя с ролью «исполнитель».
4. Постановщик не может двигать задачу за исполнителя: «Взять в работу» и «Отправить на проверку» доступны только назначенному исполнителю, строго по таблице переходов. «Принята» — конечный статус.
5. Комментарий обязателен только при возврате на доработку. Пустой комментарий или комментарий из одних пробелов не принимается. При других переходах комментарий не запрашивается.
6. Все пользователи видят имена других пользователей: это нужно для истории и выбора исполнителя. Email и пароли не показываются.
7. Если задачу переназначили, прежний исполнитель перестаёт её видеть вместе с историей.
8. Для исполнителя «нет задачи» и «чужая задача» выглядят одинаково («Не найдено»), поэтому чужие id нельзя угадать.
9. Администратор базы (доступ к дашборду Supabase) технически может всё. Защита рассчитана на пользователей приложения и прямые запросы к API.

**Не успели / можно улучшить:** realtime-обновления, пагинация и серверный поиск, аудит изменений полей задачи (сейчас пишется только история статусов), soft delete, e2e-тесты.

## Коротко для руководителя

Система хранит объекты (стройки) и задачи по ним. Каждый сотрудник входит под своим логином и паролем. Зарегистрироваться самостоятельно нельзя: учётные записи заводит администратор.

Ролей две. Постановщик создаёт объекты и задачи, назначает исполнителя, принимает работу или возвращает её на доработку с обязательным комментарием. Исполнитель видит только свои задачи и стройки, где они есть. Он может взять задачу в работу и отправить её на проверку, больше ничего.

Правила проверяет сама база данных, а не экран. Если исполнитель разбирается в программировании и отправит запрос напрямую, минуя интерфейс, база всё равно не отдаст ему чужие задачи и не позволит принять собственную работу, перескочить через этап или удалить задачу.

Каждая смена статуса автоматически записывается в историю: кто, когда, из какого статуса в какой и с каким комментарием. Эту историю нельзя изменить или стереть через приложение, даже постановщику. Секретные ключи доступа к базе в приложение и в код не попадают.
